# Looker Studio dashboard plan

Build a report that explains its conclusion without a presenter. The
challenge requires a public link. The project generates the dashboard CSVs;
the Looker Studio report and public link must still be created.

For detailed page-by-page build steps, chart settings, filters and ready-to-use
text, see [REPORT_BUILD_GUIDE.md](REPORT_BUILD_GUIDE.md).

## Story and page order

### Page 1: The answer

**Title:** Three sorcerers show the strongest RCT evidence.

| Sorcerer ID | Name | Grade | School | Qualifying visits |
|---|---|---|---|---:|
| S-0009 | Jin Hirose | 1 | Kyoto | 4 |
| S-0101 | Yui Tsukishima | Special | Tokyo | 4 |
| S-0533 | Saki Enomoto | Special | Kyoto | 4 |

**Copy for the page:**

> These three active sorcerers each have four qualifying visits. Each visit
> has recorded severity 4 or 5, estimated recovery under 24 hours, sustained
> positive CE readings from an attributed v2.2/v2.4 device, and no recorded
> overlapping healer session. This is a data-backed screen, not proof of
> ability.

Use three scorecards and the table above. Add a link or navigation button to
the evidence page.

### Page 2: Evidence for each candidate

Add sorcerer and visit selectors.

1. **Recovery bar chart:** one bar per qualifying visit, recovery hours on
   the value axis and a 24-hour reference line.
2. **CE line chart:** reading timestamp in UTC on the X-axis, CE level on
   the Y-axis, and zero as a reference. Filter to one visit so separate stays
   are not joined into a misleading line.
3. **Visit table:** sorcerer ID, visit ID, recorded severity, UTC admission
   and discharge, recovery hours, device, firmware, longest positive hourly
   streak, and recorded healer overlap.

**Copy for the page:**

> Each candidate has four qualifying visits. The 12 visits contain 99
> attributed v2.2/v2.4 readings during the stays; all 99 recorded readings
> are positive. Absence of a recorded healer session is not proof that no
> assistance occurred.

The visit-level evidence and exact IDs are in
[answers.txt](../target/answers.txt). Recovery and admission times are based
on the documented inferred timestamp rule.

### Page 3: Road to the answer

## Data sources

The seven UTF-8 CSVs in [`dashboard_data\`](dashboard_data) are generated by
`dashboard\export.py` from the current databases and use the same screening
rule as `src\rct.py`. Run
`python -B .\dashboard\export.py` from the project root to rebuild only
these exports, or `python -B .\src` to rebuild the whole pipeline including
the exports. To write elsewhere, pass `--output <folder>` to the export script.

| CSV | Grain | Suggested fields |
|---|---|---|
| `candidates.csv` | One row per candidate | `sorcerer_id`, `name`, `grade`, `school`, `qualifying_visits` |
| `visits.csv` | One row per qualifying visit | ID, visit, severity, UTC times, recovery hours, first positive device and firmware, longest streak, healer status, timestamp assumption |
| `readings.csv` | One row per reading within a qualifying visit | IDs, device, UTC timestamp, `timestamp_display_utc`, CE level, firmware |
| `stages.csv` | One row per candidate per stage | `stage_order`, `stage`, `sorcerer_id`, `included` (1 or 0), `qualifying_visits`, `reason` |
| `rejection_evidence.csv` | One row per earlier qualifying visit of a dropped candidate | Stage, sorcerer and visit IDs, before/after recovery hours, overlapping healer sessions, reason |
| `timing_quality.csv` | One row per interpretation | `interpretation`, `negative_intervals`, `unresolved_intervals` |
| `firmware_quality.csv` | One row per firmware | `firmware`, `total_readings`, `positive_readings`, `positive_rate` (fraction from 0 to 1) |

`final.db` contains curated visits, sorcerers and attributed readings;
`data.db` contains original tables, healer overlap views and correction
history. Filter readings by both the sorcerer and the half-open UTC visit
interval `[admission, discharge)`. Include negative and zero readings if
present. Do not count visits from the reading table: a visit has multiple
readings and would be counted multiple times.

`stages.csv` reruns diagnostic screens on the **current selected drop**, not
historical snapshots. Do not label its stages as verified historical Drop 0
or Drop 1 results. For the historical timeline above, the submission feedback
is reported by the user. When healer data is absent, visit healer status
explicitly says it is unknown.

For the diagnostic progression chart, use `stage` as the dimension and
`SUM(included)` as the metric. Use `rejection_evidence.csv` in a separate
table to show the affected visits and actual healer session IDs; a candidate
can fall below the two-visit threshold even if one of their visits is not
itself affected.

## Build and share

1. In Looker Studio choose **Create > Data source >
   CSV file upload** and connect each dataset.
2. Check field types; use numeric fields for hours and CE, and parse
   `timestamp_display_utc` with `PARSE_DATETIME("%Y-%m-%d %H:%M:%S",
   timestamp_display_utc)` for the UTC line chart. Format `positive_rate` as
   a percentage.
3. Build the pages in the order above. Test both selectors on the evidence
   page, and confirm the candidate, visit and reading counts.
4. Set the report to be viewable by anyone with the link; test the link in a
   private browser window before sending it to the jury. Only publish data
   intended for public sharing.

Uploading another CSV to an existing dataset **appends** rows and can create
duplicates. Replace or recreate the dataset instead of blindly uploading the
same data again. See
[Google's CSV upload guide](https://docs.cloud.google.com/looker/docs/studio/upload-csv-files-to-looker-studio).
